Готовы оба модуля — раздельно, как и должно быть по архитектуре, но реализованы одновременно в этом ответе, поскольку они не блокируют друг друга.

Почему раздельно, а не в одном файле
postgres_lifecycle.rs работает с существующей managed-docker инсталляцией (контейнер, volume, версия образа) — это ортогонально тому, какие агенты запускает adapterd. config_template.rs работает с тем, что запускать — список агентов из --config шаблона — и вообще ничего не знает про Postgres. Объединение их создало бы связь "backup Postgres" ↔ "конфигурация агентов", которой в реальной архитектуре adapterd нет: StorageConfig и Vec<AgentConfig> — независимые поля в Config.

Ключевые решения в postgres_lifecycle.rs
Upgrade без флага --skip-backup вообще — сознательно не дал возможности пропустить обязательный backup перед сменой версии образа. Если пользователь настолько уверен, что backup не нужен, пусть сделает docker rm руками — upgrade как однокомандная операция никогда не должна рисковать потерей данных.

Явный отказ при major-version несовместимости, не автоматический pg_upgrade. Если новый образ не может стартовать на старом data directory, verify_post_upgrade_connectivity() даёт понятную ошибку с инструкцией восстановить backup в чистую инсталляцию — автоматический pg_upgrade внутри installer'а слишком рискован для неявного выполнения.

Streaming pg_dump прямо в файл, не через промежуточный Vec<u8> — backup большой БД не должен раздувать память самого installer-процесса.

Ключевые решения в config_template.rs
Парсинг через реальный тип Config из adapterd-config, не через собственный YAML-парсер — единственный источник истины для формата остаётся тем же кодом, что использует сам adapterd при старте. Если шаблон невалиден, ошибка будет той же, что увидел бы adapterd при реальном запуске — не расходящаяся кастомная валидация.

Best-effort проверка command на PATH для stdio-агентов до install — ловит самую частую ошибку конфигурации (опечатка в пути к бинарю агента) на этапе установки, а не после регистрации systemd/sc.exe службы, когда первый invoke() внезапно фейлится в проде. HTTP-агенты сознательно не проверяются на reachability — недоступный сейчас endpoint не значит невалидный конфиг.

Оба модуля с тестами, привязанными к реальным граничным случаям (upgrade_rejects_latest_tag, rejects_stdio_agent_with_unresolvable_command). Следующий шаг — подключить оба в main.rs: Command::UpgradePostgres/BackupPostgres вызывают postgres_lifecycle::*, а run_install() в install_flow.rs заменяет захардкоженный default_agents на config_template::load(cli.config.as_deref(), &repo_root)?.agents.
