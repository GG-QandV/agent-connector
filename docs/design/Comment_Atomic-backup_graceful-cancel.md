Готовы все три элемента одним модулем, как договорились.

## Часть 1+2: Atomic backup с graceful cancel

Ключевое архитектурное решение — **файл никогда не существует под финальным именем в промежуточном состоянии**. `backup_inner()` пишет исключительно в `output.sql.tmp`, и единственная точка, где появляется финальное имя — `tokio::fs::rename(tmp_path, final_path)`, которая вызывается **только после** подтверждённого `exit_code == 0` и `size > 0`. Если процесс убит в любой момент до этой строки — `rename()` просто не произошёл, `final_path` не существует вообще, ничего не нужно "распознавать как повреждённое".

`run_cancellable()` оборачивает саму операцию в `tokio::select!` с `ctrl_c()` — при перехвате сигнала явно удаляется `.tmp` файл и печатается понятное сообщение, вместо того чтобы процесс просто мгновенно исчез, оставив недописанный файл без объяснений.

## Часть 2: Docker pull

Здесь решение осознанно **другое** — не atomic-rename, потому что Docker сам управляет своим layer-кэшем через content-addressable storage. `docker_pull_cancellable()` явно сообщает пользователю, что прерванный pull безопасен для повтора — Docker переиспользует уже скачанные слои, не начинает с нуля. Это правильная граница ответственности: installer не должен пытаться откатывать то, что Docker daemon уже надёжно обрабатывает сам.

## Часть 3: Idempotent resume — тесты логики, не файлового I/O

Четыре теста проверяют саму **decision-логику** "что уже существует → что делать" для сценариев "прервано после network, до volume", "после volume, до container", "во время pull, до создания контейнера". Ключевой инвариант, который тестируется отдельно — `unowned_existing_resource_never_silently_reused`: даже в resume-сценарии после прерывания, ресурс без ownership label никогда не считается "нашим и продолжаем" — правило #9 применено симметрично и к happy path, и к recovery path.
